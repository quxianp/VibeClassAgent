## 1. 复刻前你需要准备什么

### 1.1 必须

| 项 | 版本 | 用途 | 检测命令 |
|---|---|---|---|
| Windows | 10 及以上 | 运行平台 | `winver` |
| Rust 工具链 | stable  1.75 | 编译宿主 | `cargo --version` |
| C++ 构建工具 | MSVC 或 MinGW | 链接 | 见下 |

### 1.2 可选（不装也能编译运行，只影响对应功能）

| 项 | 用途 | 检测 |
|---|---|---|
| Python  3.10 | 转写 / 文档生成 | `python --version` |
| ffmpeg | 实际录屏录音 | `ffmpeg -version` |
| LibreOffice | Word 转 PDF | `soffice --version` |
| ClassIsland | 课表来源（若学校在用） |  |

### 1.3 关于 C++ 构建工具（最容易卡住的一步）

Rust 在 Windows 上有两个目标：

| 目标 | 需要 | 说明 |
|---|---|---|
| `x86_64-pc-windows-msvc` | **MSVC 链接器**（`link.exe`） | 默认，推荐 |
| `x86_64-pc-windows-gnu` | **MinGW 链接器**（`ld.exe`/`gcc`） | 备用 |

**推荐做法**：装 Visual Studio Build Tools，勾选「使用 C++ 的桌面开发」。
只要装了它，后面什么都不用操心。

**怎么判断有没有装好**：

```powershell
# 找 vswhere（VS 安装器自带的探测工具）
$vswhere = "${env:ProgramFiles(x86)}\Microsoft Visual Studio\Installer\vswhere.exe"
& $vswhere -latest -products * -requires Microsoft.VisualStudio.Component.VC.Tools.x86.x64 -property installationPath

# 关键：能不能找到 link.exe
Get-ChildItem "C:\Program Files (x86)\Microsoft Visual Studio" -Recurse -Filter link.exe -ErrorAction SilentlyContinue | Select-Object -First 3 -ExpandProperty FullName
```

>  **注意**：装了 Build Tools **不等于**装了 C++ 工作负载。
> 本机就是「有 Build Tools 但没 C++ 工作负载」，`link.exe` 找不到，
> 所以才走了 GNU 路线（见 [5](#5-本机受限环境的绕行方案)）。

## 5. 本机受限环境的绕行方案

**如果你的机器是正常的，跳过本节。** 本节记录本机遇到的四个限制与解法，供同类环境参考。

### 5.1 症状与原因

| # | 症状 | 原因 |
|---|---|---|
| 1 | `cargo` / `rustc` 命令不存在 | 未安装 Rust |
| 2 | 装不了（`Access denied`） | `C:\Users\<user>` 无写权限 |
| 3 | `ld: cannot find -lXXX` / `unrecognized option '--high-entropy-va'` | 缺 MSVC 链接器；PATH 里有 Dev-Cpp 的旧 MinGW |
| 4 | `schannel: SEC_E_NO_CREDENTIALS` | cargo 的 TLS 被沙箱阻断 |

### 5.2 解法一：工具链装到工作区内（对应 #1 #2）

```powershell
# 1) 下载 rustup-init.exe（用 Python 的 urllib，走 OpenSSL，不受 schannel 影响）
#    国内建议用 USTC 镜像
$url = "https://mirrors.ustc.edu.cn/rust-static/rustup/dist/x86_64-pc-windows-msvc/rustup-init.exe"

# 2) 指定 CARGO_HOME / RUSTUP_HOME 到工作区
$env:CARGO_HOME  = "D:\VibeClassAgent\.toolchain\cargo"
$env:RUSTUP_HOME = "D:\VibeClassAgent\.toolchain\rustup"
$env:RUSTUP_DIST_SERVER = "https://mirrors.ustc.edu.cn/rust-static"

# 3) 用 GNU 目标安装（自带链接器，绕开 MSVC 缺失）
.\rustup-init.exe -y --no-modify-path --profile minimal --default-toolchain stable-x86_64-pc-windows-gnu

# 4) 装可选组件
rustup component add rustfmt clippy
```

`.toolchain/` 已被 `.gitignore` 排除，**不会入库**。

### 5.3 解法二：剔除旧 MinGW（对应 #3）

PATH 里若有 `D:\Dev-Cpp\MinGW64`（GCC 4.9.2），rustc 会误选它的 `ld`。
`scripts/dev.ps1` 已自动剔除。手工操作时：

```powershell
$clean = ($env:PATH -split ';' | Where-Object { $_ -and ($_ -notlike '*Dev-Cpp*') }) -join ';'
$env:PATH = "$env:CARGO_HOME\bin;$clean"
```

**并且不要用 `SetWindowRgn` 做圆角**（1 位掩码，锯齿），改用分层窗口逐像素 Alpha。
另外**不要链接 dwmapi**GNU 工具链自带的导入库里没有 `libdwmapi.a`。

### 5.4 解法三：本地 HTTP 代理转发 crates.io（对应 #4）

cargo 用 schannel，被阻断；Python 用 OpenSSL，能联网。于是：

1. 起一个**只监听 127.0.0.1** 的小代理，把 crates.io 的稀疏索引与 crate 下载转发出去；
2. 让 cargo 指向它。

`.toolchain/cargo/config.toml`：

```toml
[source.crates-io]
replace-with = "local-proxy"

[source.local-proxy]
registry = "sparse+http://127.0.0.1:8787/"
```

> 正常网络下**不需要**这个，删掉该文件即可走官方源。

### 5.5 解法四：避开 raw-dylib

`uuid` 会经 `getrandom` 触发 **raw-dylib** 链接，需要 `dlltool` 生成导入库，
在 GNU 工具链下这一步会失败。同理 `chrono` 的时区支持也引入类似依赖。

**本项目的做法**：核心层不引入它们，
时间用自研的 `vca-core/src/time.rs`（civil 日期算法，零依赖），
ID 用「日期+时间+课程」拼字符串。装好 MSVC 后可以按需加回来。

## 6. 配置一台真实一体机

### 6.1 最小可用配置

```powershell
# 1) 编译发布版
cargo build --release

# 2) 准备配置目录
mkdir C:\ProgramData\VibeClassAgent\config\profiles\default
copy config\settings.example.yaml C:\ProgramData\VibeClassAgent\config\profiles\default\settings.yaml
copy config\timetable.example.yaml C:\ProgramData\VibeClassAgent\config\timetable\current.yaml
copy config\schedule.example.yaml C:\ProgramData\VibeClassAgent\config\schedule\current.yaml

# 3) 编辑这两份（见《课程表与时间表编辑文档》）

# 4) 设置密钥（绝不写进配置文件）
[Environment]::SetEnvironmentVariable("VCA_LLM_API_KEY", "<你的Key>", "User")
[Environment]::SetEnvironmentVariable("VCA_PUSH_ENDPOINT", "<企业微信Webhook>", "User")
[Environment]::SetEnvironmentVariable("VCA_PUSH_TOKEN", "<token>", "User")

# 5) 自检
.\target\release\vca.exe doctor

# 6) 试运行（不真正录制/推送）
.\target\release\vca.exe run --dry-run
```

### 6.2 设为开机自启（推荐用计划任务，**不要用服务**）

| 方式 | 能否采集桌面 | 结论 |
|---|---|---|
| Windows 服务 |  Session 0 隔离，抓不到桌面 | **不可用** |
| 计划任务（用户登录时触发） |  | **推荐** |
| 启动文件夹快捷方式 |  | 简单但不如计划任务可控 |

计划任务配置要点：

```powershell
$action  = New-ScheduledTaskAction -Execute "C:\ProgramData\VibeClassAgent\vca.exe" -Argument "run"
$trigger = New-ScheduledTaskTrigger -AtLogOn
$settings = New-ScheduledTaskSettingsSet -AllowStartIfOnBatteries -DontStopIfGoingOnBatteries -ExecutionTimeLimit ([TimeSpan]::Zero)

Register-ScheduledTask -TaskName "VibeClassAgent" -Action $action -Trigger $trigger -Settings $settings -RunLevel Highest
```

> `-ExecutionTimeLimit 0` 表示不限制运行时长（守护进程要长期跑）。

### 6.3 静默性确认

- 无窗口、无弹窗、无气泡；
- 只有**一个小托盘图标**（若 `ui.tray_icon: true`）；
- ffmpeg 与 Python 子进程都以 `CREATE_NO_WINDOW` 启动；
- 崩溃时 `SetErrorMode` 屏蔽系统错误对话框。

## 7. 常见坑

### 7.1 `cargo build` 报 `unrecognized option '--high-entropy-va'`

PATH 里有旧 MinGW。解法见 [5.3](#53-解法二剔除旧-mingw对应-3)。

### 7.2 `ld: cannot find -ldwmapi`

GNU 工具链自带导入库不含 dwmapi。**不要链接 dwmapi**本项目改用
`user32.SetWindowCompositionAttribute` 或纯自绘实现玻璃效果。

### 7.3 悬浮窗文字不显示 / 圆角有锯齿

这是本项目**真实踩过的坑**，记录在此避免重犯：

| 现象 | 根因 | 正确做法 |
|---|---|---|
| 整窗纯色、**没有文字** | 用了 `SetWindowCompositionAttribute` + `ACCENT_ENABLE_ACRYLICBLURBEHIND`，DWM 接管背景后把本进程 GDI 绘制覆盖掉 | 改用 `WS_EX_LAYERED`，背景与文字**都由自己绘制** |
| 圆角**锯齿明显** | `SetWindowRgn` 的窗口区域是 **1 位掩码**，物理上无法抗锯齿 | 改用 `UpdateLayeredWindow` + 逐像素 Alpha，圆角覆盖率用 **44 超采样**算 |
| 有底无字 | `DrawTextW` 前 `GetClientRect` 失败返回全 0 矩形 | 直接用样式里已知的宽高构造绘制矩形 |
| 文字边缘也锯齿 | GDI 直接画在目标位图上拿不到 Alpha | 先画到「黑底白字」临时 DIB，再按 `覆盖率 = 亮度` 反解并合成 |

最终实现在 `crates/vca-platform/src/overlay.rs` 的 `render_layered()`。

### 7.4 Python Worker 输出中文乱码

Windows 管道默认用区域编码（GBK），协议约定 UTF-8。
`rpc.py` 的 `ensure_utf8_stdio()` 已强制切换，**不要删掉它**。

### 7.5 PowerShell 脚本中文乱码

`.ps1` 必须存为 **UTF-8 with BOM**（PowerShell 5.1 会把无 BOM 的 UTF-8 当 GBK）。
`.cmd` 里**不要写中文注释**（cmd 用 GBK 读文件，会破坏语法）。

### 7.6 `cargo test` 偶发 `memory allocation failed`

编译并发过高。用 `cargo test -j 1` 或 `cargo build -j 1`。

### 7.7 改完配置没生效

- 确认改的是 `current.yaml`，不是 `.example.yaml`，也不是 `archive/` 里的存档；
- 守护进程需重启（配置在启动时载入一次）。

## 附录 E：release 构建与体积优化（重要修复）

### E.1 症状

`cargo build`（debug）正常，但 `cargo build --release` 报：

```
error: error calling dlltool 'dlltool.exe': program not found
error: could not compile `windows-sys` (lib)
```

把 Rust 自带的 `dlltool.exe` 加进 PATH 后，变成：

```
error: dlltool could not create import library with ... -d kernel32.dll_imports.def
```

### E.2 根因

`windows-sys` 用了 **raw-dylib** 链接方式，需要 `dlltool` 在链接期生成导入库；
而本机的 GNU 工具链下 `dlltool` 会失败。

**`windows-sys` 从哪来？** 用 `cargo tree -i windows-sys` 查：

```
windows-sys v0.61.2
 anstyle-query    anstream  clap_builder  clap  vca-cli
 anstyle-wincon   anstream （同上）
 nu-ansi-term     tracing-subscriber  vca-cli
```

**结论：全部只来自「终端彩色输出」**。

### E.3 修复

一个后台守护进程**根本不需要彩色终端**。关掉这两个特性即可从依赖树里彻底移除 `windows-sys`：

```toml
# Cargo.toml
clap = { version = "4", default-features = false,
         features = ["std", "derive", "help", "usage", "error-context", "suggestions"] }

tracing-subscriber = { version = "0.3", default-features = false,
                       features = ["std", "fmt", "env-filter"] }
```

同时移除了 `panic = "abort"`（它会破坏 `crash::guard` 的 `catch_unwind`）。

### E.4 效果

| 项 | 修复前 | 修复后 |
|---|---|---|
| `cargo build --release` |  dlltool 失败 |  成功 |
| 依赖树中的 windows-sys | 有 | **无** |
| `vca.exe` 体积 |  | **1,921 KB（约 1.9 MB）** |
| 崩溃静默退出 | 正常 | 正常（`catch_unwind` 也可用） |

**体积为什么这么小**：`opt-level = "z"` + `lto = "thin"` + `codegen-units = 1` + `strip = true`。
这也符合「极低系统占用」的项目目标。

### E.5 给复刻者的提示

如果在别的机器上 `cargo build --release` 也报 dlltool 错误：
**优先检查是不是有依赖引入了终端配色**（`anstream` / `nu-ansi-term` / `windows-sys`）。
把对应的 `color` / `ansi` 特性关掉，比去修 dlltool 简单得多，而且顺带减小体积。
